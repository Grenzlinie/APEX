# APEX 2.0 工程方向

本文档是工程方向说明，不是功能承诺。用它来在实现前对齐设计，并让 `AGENTS.md` 保持为开发契约。

## 目标

- 让新贡献者更容易理解、测试和扩展 APEX。
- 保留当前 CLI 和 JSON 驱动 workflow，同时支持 agent 和 skill 化使用。
- 通过减少隐藏 fallback、陈旧依赖和不清楚的执行边界来提升鲁棒性。
- 让测试更接近真实计算 workflow，同时不要求每个贡献者都运行昂贵的外部任务。

## 方向 1：Subagent 辅助性质流程

- Subagents 可以提出新的性质 workflow、测试和对抗式 review 用例。
- 科学假设、公开 schema 和验收标准仍必须经过人类 review。
- 生成的 workflow 只有在具备确定性 fixture、真实感后处理测试和文档后，才能视为支持能力。

## 方向 2：结构建模

- 建模应支持明确的 CLI 输入和 agent/skill 交互，同时对模糊选择保留人类确认。
- 无效或不完整结构应清楚失败或请求缺失信息；不要静默替换为猜测结构。
- 生成结构必须留下可检查 artifact 和 provenance。

## 方向 3：Skill 化 APEX 使用

- Skill 应包装稳定的 APEX 命令，并检查明确文件或目录。
- Skill 行为不能依赖隐藏聊天状态、未跟踪凭证或隐式工作目录假设。
- 现有 CLI 使用方式仍是兼容性基线。

## 方向 4：Workflow 后端解耦

- dflow/Argo 解耦应先隔离提交、监控、回收和失败报告边界。
- 替换前必须为现有 dflow 行为建立兼容测试。
- DPDispatcher 和可能的 Bohr CLI 集成应作为后端 adapter 评估，不应混入科学性质逻辑。

## 方向 5：开发体验与 CI/CD

- 贡献者环境应能通过文档化命令复现。
- CI 应包含确定性单元测试，并对真实感任务生成、解析和失败行为做针对性检查。
- 外部集成测试应为 opt-in，有明确文档，并能清楚报告缺少凭证或可执行文件。

## 未经明确批准不做的事

- 移除现有 CLI/JSON workflow。
- 在没有迁移路径的情况下移除 dflow/Argo 支持。
- 改变公开参数键或输出目录约定。
- 引入隐藏 fallback，从而掩盖缺失 API、命令、凭证或无效科学输入。

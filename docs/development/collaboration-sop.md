# 人类-Codex 协作 SOP

非平凡 APEX 改动应遵循本 SOP。小范围 typo 修复和窄文档编辑不需要完整 workplan。

## 编辑前

- 阅读相关代码、测试、示例和文档。
- 用“当前行为”和“期望行为”描述问题。
- 识别受影响的公开接口：CLI、JSON schema、输出目录、archive 数据、报告、依赖、镜像或文档。
- 判断是否需要真实 API 访问、凭证、外部可执行文件或接近生产的数据。
- 当改动影响架构、公开行为、依赖、workflow 后端或科学结果时，在 `.codex/workplans/` 下写本地 workplan。

## Workplan 模板

```md
# 标题

## 目标

要解决什么问题，面向谁？

## 当前证据

已检查的文件、测试、命令、日志或示例。

## 拟议变更

行为层面的计划、公开接口、迁移影响，以及预计会改动的文件。

## 保留要求

哪些现有行为不能改变。

## 测试证据

单元测试、fixture 更新、真实集成检查，以及是否需要人类提供 API/数据。

## 提交计划

小提交或 PR 切片。
```

## 实现中

- 将改动限制在已确认的范围内。
- 优先使用显式错误，而不是隐藏 fallback。
- 除非已确认迁移，否则保留现有用户 workflow。
- 测试应随实现一起更新，而不是最后补。
- 用户可见行为变化时，同步更新 README/examples 和 `CHANGELOG.md`。

## 收尾前

- 先运行最小相关测试；当共享路径或公开行为变化时扩大验证范围。
- 检查 `git status --short` 和 `git diff`。
- 汇报改了什么、保留了什么、运行了哪些测试、哪些测试没跑，以及剩余依赖或环境阻塞。
- 保持提交聚焦，确保单个功能或修复可以回撤。
